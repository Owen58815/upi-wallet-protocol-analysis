# 海外支付钱包协议开发与定制

团队长期做 Android 逆向、支付协议分析和客户端定制，目前主要研究印度 UPI，同时覆盖孟加拉、拉美、东南亚部分主流支付平台。

做这类项目比较多，我简单整理一下目前能够提供的服务和交付方式，方便有相关需求的客户了解。

## 一、目前主要研究的平台

| 地区      | 平台                                                                                                                                                                      |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **印度**  | PhonePe、PhonePe Business、Paytm、Paytm Business、MobiKwik、FreeCharge、MyJio、GPay、GPay Business、MoneyView、BharatPe Business、super.money、Navi、Amazon Pay、Airtel、BHIM IndusPay |
| **孟加拉** | bKash、Nagad                                                                                                                                                             |
| **拉美**  | Mercado Pago                                                                                                                                                            |
| **东南亚** | TrueMoney                                                                                                                                                               |

印度目前是我们研究比较多的市场。

主要原因是 UPI 支付体系成熟，钱包数量多，个人版、Business 商业版都有，实际项目需求也比较多。

不同钱包功能差异比较大，有些偏个人 UPI，有些主要做商户收款，有些同时包含钱包、银行账户、UPI、信贷等业务。

所以具体项目开始之前，一般会先根据客户需要的业务场景确定平台。

## 二、主要做哪些内容

### 1. 钱包协议

针对指定钱包和版本分析客户端协议。

常见内容包括：

- OTP 登录
- Token 获取和刷新
- 用户信息
- UPI ID / VPA
- 银行账户
- 余额
- 流水列表
- 流水详情
- 交易状态
- 商户订单
- 收款记录
- Settlement / 结算
- 其他项目需要的接口

完成后整理协议文档。

根据项目情况，可以同时提供 Java / Python 参考代码，方便后台直接集成。

## 三、Business 商业版协议

除了普通个人钱包，我们比较关注 Business 版本。

例如：

PhonePe Business  
Paytm Business  
GPay Business  
BharatPe Business

个人钱包和 Business 钱包的业务逻辑不完全一样。

个人版更多是：

**UPI ID、银行卡、转账、收款、流水。**

Business 版更多是：

**Merchant、QR、订单、收款流水、交易状态、对账、Settlement。**

如果项目主要做商户收款、订单核销，一般优先研究 Business 版本。

具体支持哪些能力，需要根据钱包和当前版本实际分析。

## 四、钱包客户端定制

除了协议，也可以根据项目需要做 Android 客户端定制。

例如：

**官方钱包 → 定制客户端 → 获取实时流水 → 上传客户后台 → 匹配订单 → 完成核销**

这类项目最终交付一个可以实际使用的 APK。

客户端负责账户登录、流水获取、状态同步等功能，客户后台按照我们提供的接口文档进行对接。

具体功能按照项目需求定制，不做固定模板。

## 五、协议 + 客户端一起交付

有些客户不只是需要 APK，还希望自己后台能够掌握协议。

这种一般采用：

**定制 APK + 协议文档 + Java/Python 参考源码**

三部分一起交付。

客户后续可以自己完成服务器集成，我们负责钱包客户端和协议部分。

这样做的好处是项目不会完全依赖某一个 APK，后续扩展账户管理、流水核销、订单系统也方便很多。

## 六、商业接口、协议和客户端方案

实际项目中通常有三种方案。

| 方案     | 特点                    | 适合场景           |
| ------ | --------------------- | -------------- |
| 官方商业接口 | 稳定，维护成本低，但需要资质，开放能力有限 | 正规商户业务         |
| 钱包协议   | 后台可以直接集成，自动化程度高       | 有服务器开发能力的项目    |
| 定制客户端  | 可以结合真实客户端环境完成业务       | 对客户端能力依赖比较强的项目 |

没有哪一种方案适合所有钱包。

我们一般先看客户需要什么功能，再确定走官方接口、协议还是客户端方案。

## 七、代收和代付

这个需要根据具体钱包区分。

不能简单认为一个钱包支持转账，就一定适合商业代付。

我们通常会把平台分成：

**个人收付型**

主要关注：

UPI Pay、Receive、银行账户、UPI ID、流水。

**Business 代收型**

主要关注：

Merchant QR、Collection、订单、交易流水、Settlement。

**商业付款型**

主要看平台有没有正式的 Payout / Disbursement / Banking API。

项目开始前可以根据客户需要的国家、钱包和业务模式，先确认对应平台具备哪些能力，再决定开发方案。

## 八、服务器和稳定性

协议跑通只是第一步。

真正长期使用以后，还会涉及：

Token 生命周期、设备绑定、版本变化、请求频率、服务器网络、失败重试、账户状态、交易同步等问题。

所以实际交付的时候，我们会尽量把这些问题一起考虑进去。

如果客户自己有后台开发团队，我们提供协议和接口说明。

如果需要完整方案，也可以按照实际业务设计：

**钱包 → 客户端/协议服务 → 流水同步 → 订单匹配 → 核销**

## 九、版本更新和维护

支付钱包更新比较频繁。

App 升级以后，可能出现：

接口版本变化、Header 变化、Token 变化、参数变化、返回结构变化、设备绑定变化等情况。

所以这类项目不能只看第一次能不能跑通，还要考虑后续维护。

我们可以提供持续更新服务。

官方钱包升级以后，根据新版本重新分析变化部分，更新协议、代码或者客户端。

对于长期项目，建议采用：

**首次开发 + 后续维护**

这种合作方式。

## 十、交付内容

根据项目不同，可以单独或者组合交付：

**协议类**

协议文档  
接口说明  
请求/响应字段说明  
Java / Python Demo  
参考源码

**客户端类**

定制 APK  
客户端源码  
后台对接接口  
部署说明

**长期维护**

官方版本更新分析  
协议更新  
客户端兼容  
接口修复  
文档更新

具体交付哪些内容，在项目开始之前确定清楚。

## 十一、合作方式

客户提供：

**国家 + 钱包名称 + 需要的功能**

例如：

> 印度 PhonePe Business  
> 需要登录、获取商户信息、实时流水、流水详情、交易状态。

我们先分析当前版本和需求，再确定：

**能不能做 → 采用什么方案 → 交付哪些东西 → 开发周期 → 后续维护方式**

如果是没有研究过的新钱包，也可以先做技术分析。

目前重点还是印度 UPI，后续会继续增加孟加拉、拉美和东南亚支付平台。

这类项目我们更看重长期维护。

一个钱包协议分析出来并不难，真正麻烦的是官方不断升级以后，还能不能快速找到变化、更新协议，让原来的项目继续稳定使用。
